# Production operations and recovery

## Configuration (Cloudflare Workers)

Set `NEXT_PUBLIC_SUPABASE_URL` and `NEXT_PUBLIC_SUPABASE_ANON_KEY` at **build time** and as Worker runtime variables; these are publishable Auth-only values, not a service-role key. Set `TURSO_DATABASE_URL`, `TURSO_AUTH_TOKEN` and `APP_ORIGIN` only as Worker runtime secrets (`wrangler secret put NAME`); Turso values must never use `NEXT_PUBLIC_`. `APP_ORIGIN` is the exact public HTTPS origin without a trailing slash. The optional `RATE_<ACTION>_MAX` and `RATE_<ACTION>_WINDOW_SECONDS` variables tune bounded database rate limits (see `src/lib/forum/rate.ts`). See `.env.example` and `.dev.vars.example` for names, never real tokens.

Deploy with `npm run cf:build && npm run cf:deploy` after migrating production Turso. OpenNext requires `nodejs_compat`; forum DB traffic uses `@libsql/client/web` over HTTPS (no local SQLite/Node sockets in the Worker). `next.config.ts` traces the libSQL web adapter's WebSocket shim needed by OpenNext. Do **not** add server secrets to `next.config.ts` `env`, `NEXT_PUBLIC_*`, client components, or CI logs. Automated CI uses only fake localhost services; no deployment credentials are required.

## Supabase Auth production checklist

- Configure Authentication → URL Configuration: **Site URL** = exact production `APP_ORIGIN`; Redirect URLs = `https://YOUR_DOMAIN/auth/callback` (and explicitly authorized staging origins). Remove unneeded wildcards and development origins from production. Magic links must use the PKCE callback.
- Enable Email magic links with a verified SMTP sender/domain. Set suitable OTP expiry and email send limits. Review Supabase Auth abuse/rate-limit settings (email OTP/IP, token refresh, verification) and alert on anomalous sends. Anyone with the public anon key can call Supabase Auth directly; the app's login rate limit cannot replace Supabase's platform limits.
- Disable unwanted providers/signups if appropriate; configure email confirmation and account-security policy. Keep the publishable/anon key separate from Supabase **service-role** credentials. The app does not need or store a service-role key, nor use Supabase database. Supabase owns token expiry/refresh; SSR cookies use the Supabase SSR package with `HttpOnly` and `SameSite=Lax` (and `Secure` when `APP_ORIGIN` is HTTPS). Auth is server-only: do not add a browser Supabase client that needs to read these cookies. Production sign-in rejects non-HTTPS `APP_ORIGIN`. Authenticated user IDs are checked with `getUser()` rather than trusting unverified client state.
- Test magic links from a real production/staging mailbox after configuring `APP_ORIGIN`, cookie domain/HTTPS, and allowed redirects. Enforce HTTPS (including Cloudflare Always Use HTTPS/HSTS _after_ confirming the domain).

## R2 avatars

Create **private** R2 bucket: `npx wrangler r2 bucket create yori-avatars`. Bind `AVATARS` to `yori-avatars` in `wrangler.jsonc`; don't attach a public bucket domain. Confirm `cf:preview` with local R2 simulation and production upload/remove. Authenticated users alone upload/delete/replace their own objects. The server limits raw upload streams to 1 MiB, compares Content-Type against PNG/JPEG/WebP magic bytes, and generates the key from user ID and a random UUID; the original filename is discarded. Public GET `/api/avatar/[id]` resolves only the currently associated profile key in Turso and serves the object with `nosniff`, strict image MIME/CSP and five-minute browser cache. The bucket is not an executable/static web host. An image may still be malformed despite magic-byte checks; consider full image decoding/re-encoding if abuse warrants it. Old-object cleanup is best effort; periodically review orphaned objects under `avatars/`.

## Backup and restore (Turso and R2)

**Turso contains all forum data**: profiles/identities (not Supabase passwords), categories, threads/posts and edit history, roles, reactions, notifications, reports, bookmarks, moderation audit, optional session metadata and temporary rate-limit counters. **R2 contains avatar image objects only**. Supabase independently owns login accounts/tokens and must be protected separately.

1. Daily (and before every migration), use Turso's platform point-in-time recovery/snapshot facilities if available on your plan. Independently export from a trusted admin workstation/CI environment using the **Turso CLI** version your account supports: `turso db shell DATABASE_NAME .dump > backup-YYYY-MM-DD.sql`. Verify the command on your installed CLI (`turso db shell --help`) because CLI versions differ. Store the dump encrypted outside Git, with restricted access and documented retention (at least 30 daily copies plus pre-migration snapshots); test a restore monthly. Do not keep dumps in `.env`, repo or CI artifacts. If export is unavailable on your plan, configure an approved read-only SQLite-compatible export workflow or rely on Turso's documented snapshot recovery; never assume an unverified backup succeeded.
2. Validate an export offline: create a **new disposable** SQLite database (`sqlite3 /tmp/yori-restore-check.db < backup.sql`); run `PRAGMA integrity_check;`, `PRAGMA foreign_key_check;`, compare table counts (`users`, `threads`, `posts`, `reports`), and inspect `__drizzle_migrations`. For a production restore, create a **new Turso database** (never overwrite a live source), import via `turso db shell NEW_DB < backup.sql` if supported by your CLI (verify `turso db shell --help`), run integrity/count checks and app smoke tests using the new database URL/token. Reconcile schema migration version before switching `TURSO_DATABASE_URL` and `TURSO_AUTH_TOKEN` Worker secrets; redeploy, verify `/api/health`, then retire old tokens. For point-in-time restore use Turso's documented recovery commands instead.
3. R2: keep the bucket private and enable an R2-supported backup/replication policy or scheduled `rclone`/S3-compatible sync to an encrypted separate destination. Back up at least daily and verify a sample avatar fetch against a restored Turso profile key; SQL alone does **not** restore images. When switching databases, preserve the same R2 binding or restore avatar objects before cutover.
4. If the Worker is down but Turso/R2 are healthy: rollback the Worker deployment using Cloudflare deployment history, check `/api/health`, and pause community writes during incident response. If Turso is down, the health endpoint returns 503; pause writes, recover into a new DB, then rotate Worker secrets as above. If R2 is down, the rest of the forum remains available; avatars fall back to initials on profiles if unconfigured, and uploads return 503. Keep an incident runbook with contact ownership and recovery time objectives.

Never upload backup dumps to a public bucket or commit credentials. Run restore drills on disposable infrastructure before declaring the strategy reliable.

## Monitoring and search

`GET /api/health` returns 200 `{status:'ok',database:'ok'}` on a successful `select 1`, otherwise 503 with a generic degraded response and `Retry-After`. It is uncached and contains no environment variables, SQL error text or credentials. Probe it externally every 1–5 minutes and alert on 503, latency spikes and Worker errors. Operational errors are logged as structured JSON (event, timestamp, exception **type only**) with no tokens, email addresses or private post content; Cloudflare observability is enabled in Wrangler. Configure log retention and alerts in Cloudflare, Turso DB availability alerts, Supabase Auth email delivery monitoring, and migration failure alerts.

Initial forum search uses bound SQL `LIKE` with an escaped pattern, correlated posts/users, visible-category predicates, a maximum 80-character query, 20 results/page and public/IP/account rate limits. Prefix indexes cannot accelerate a leading-wildcard `%term%`; current indexes efficiently support thread/category visibility and post/thread joins, but content matching scans visible threads/posts. For an initial community of a few thousand threads / roughly 10–20k posts this avoids premature FTS complexity. Benchmark real p95 query latency using `EXPLAIN QUERY PLAN` plus sampled queries after launch. If corpus approaches ~20k–50k posts, p95 search exceeds 300–500ms, or Turso read usage spikes, plan a reviewed SQLite/Turso-native FTS5 migration with triggers, backfill, soft-delete/archival filtering and rollback tests. Do not add an external search service by default.

## Dependency security

`npm audit` is reviewed before release. Production direct Drizzle ORM is pinned to a patched 0.45.x; PostCSS (including Next's nested copy) is overridden to a patched 8.5.x. Four remaining **moderate development-only** advisories in drizzle-kit's esbuild-kit/old esbuild path require an upstream update; this package is used for trusted local/CI schema generation and is not shipped to the Worker. Never expose the Drizzle Kit development server publicly. Run `npm audit --omit=dev --audit-level=high` in CI; reevaluate pinned overrides and upstream patches regularly. No blind major framework migration solely to silence a transitive dev-only advisory.
